# TCP-чат на iow: сервер и клиент

Ниже разобран минимальный, но законченный пример: TCP-сервер и TCP-клиент, которые обмениваются текстовыми строками. Это не каркас микросервиса и не JSON-RPC — только то, что нужно, чтобы несколько процессов говорили друг с другом по сети и чтобы было видно, как устроено приложение на **iow**.

**iow** — библиотека поверх Boost.Asio для потокового ввода-вывода: приём соединений, исходящие подключения, буферы чтения и записи, повторное соединение после обрыва. Внутри у неё богатый шаблонный каркас (аспекты на базе faslib), но для типичного приложения это остаётся деталью реализации. В примере используются готовые типы `server<>` и `client<>` и набор колбэков в структуре options — без объявления собственных аспектов.

Исходники:

* `examples/chat_server.cpp`
* `examples/chat_client.cpp`

## Сборка и запуск

```bash
git clone --recursive <url-репозитория-iow.git>
cd iow
git submodule update --init --recursive
mkdir build && cd build
cmake .. -DWITH_SAMPLES=ON
make chat_server chat_client
```

В одном терминале запускается сервер:

```bash
./bin/utils/chat_server 30000
```

В других — клиенты:

```bash
./bin/utils/chat_client 127.0.0.1 30000
```

Каждая введённая строка (до нажатия Enter) уходит на сервер и рассылается всем текущим участникам, включая отправителя. Клиент завершает работу по Ctrl+D (конец ввода). Если сервер временно недоступен, клиент через секунду пытается подключиться снова.

Boost в этом проекте обычно подтягивается через cmake-ci; для сборки достаточно окружения с компилятором C++14 или новее.

## Зачем вообще «резать» поток: границы сообщений

TCP отдаёт приложению непрерывный поток байт. Он не знает, где кончилась одна «логически законченная» фраза и началась следующая. Если просто читать из сокета, можно получить полстроки, две строки сразу или обрывок посередине — в зависимости от того, как сеть и ОС сложили пакеты.

Поэтому в чате (и в большинстве текстовых протоколов) нужна договорённость о **границе сообщения**. В примере граница — символ перевода строки `\n`: всё, что пришло до него, считается одной репликой; сам разделитель в текст сообщения обычно не входит.

В iow эта договорённость задаётся опциями буферов:

```cpp
opt.connection.reader.sep = "\n";
opt.connection.writer.sep = "\n";
```

* **reader** накапливает входящие данные и отдаёт в `input_handler` уже целые куски, отсечённые по `sep` (при включённом `trimsep` сам разделитель из полезной нагрузки убирается).
* **writer** при отправке дописывает `sep` к данным, чтобы на той стороне reader снова увидел ту же границу.

Без `sep` «сообщением» оказывается ровно то, что вернул один вызов `read` — для чата и JSON-RPC это, как правило, непригодно. Для бинарных протоколов с длиной в заголовке используют другой подход; строковый чат как раз хорошо ложится на разделитель.

Схема движения данных:

```
сокет / stdin  →  read_buffer (ждёт sep)     →  input_handler
send(...)      →  write_buffer (добавляет sep) →  сокет
```

Сервер держит listening-сокет и для каждого клиента — своё соединение с такими же буферами. Клиент устанавливает соединение (и при необходимости переустанавливает его после обрыва) и использует ту же пару reader/writer.

## Точки расширения соединения

Почти вся прикладная логика вешается на три колбэка в options соединения:

| Колбэк | Когда вызывается |
|--------|------------------|
| `startup_handler` | соединение установлено; передаётся `output_handler` для последующей записи в этот сокет |
| `input_handler` | собрано очередное сообщение по правилам reader |
| `shutdown_handler` | соединение закрыто (штатно или из‑за ошибки) |

Адрес, порт, разделитель, таймаут повторного подключения и прочие параметры задаются полями той же структуры options до вызова `start`.

## Сервер

Полный код — в `examples/chat_server.cpp`. Ниже — основные решения.

Типы сервера и его options берутся в конфигурации «по умолчанию»: пустые угловые скобки означают параметры шаблона по умолчанию, а не требование описывать свою иерархию типов.

```cpp
typedef iow::ip::tcp::server::server<> server_t;
typedef iow::ip::tcp::server::options<> options_t;
```

iow не знает про «комнаты» и «ники». Список участников и рассылка — обычный прикладной код: при появлении соединения в map кладётся его `output_handler`, при уходе — запись удаляется, при входящей строке — копия уходит всем известным получателям.

```cpp
std::mutex mutex;
std::map<io_id_t, output_handler_t> peers;
```

```cpp
opt.connection.startup_handler = [&](io_id_t id, output_handler_t out)
{
  std::lock_guard<std::mutex> lk(mutex);
  peers[id] = std::move(out);
};

opt.connection.shutdown_handler = [&](io_id_t id)
{
  std::lock_guard<std::mutex> lk(mutex);
  peers.erase(id);
};

opt.connection.input_handler = [&](data_ptr d, io_id_t, output_handler_t)
{
  if ( d == nullptr ) return;
  const std::string msg(d->begin(), d->end());
  std::lock_guard<std::mutex> lk(mutex);
  for (auto& p : peers)
    p.second( make(msg) );
};
```

`io_id_t` — идентификатор соединения внутри acceptor’а.  
`data_ptr` — владеющий указатель на буфер (`unique_ptr` на `vector<char>`).  
`make(msg)` — удобный конструктор такого буфера из `std::string`.

После настройки options сервер запускается, и управление передаётся циклу Asio:

```cpp
server->start(opt);
io.run();
```

Пока выполняется `io.run()`, обрабатываются новые accept’ы и события всех живых соединений. Остановка цикла останавливает и серверную активность на этом `io_context`.

В примере `threads` не задаётся (остаётся 0): accept и соединения обслуживаются на том же контексте, что и `io.run()`. Если позже понадобится разнести accept по нескольким потокам, достаточно выставить `opt.threads = N` — iow создаст дополнительные acceptor’ы через `dup()` listening-дескриптора.

## Клиент

Полный код — в `examples/chat_client.cpp`.

```cpp
typedef iow::ip::tcp::client::client<> client_t;
typedef iow::ip::tcp::client::options options_t;
```

Подключение к серверу и печать входящих строк:

```cpp
opt.addr = host;
opt.port = port;
opt.async_connect = true;
opt.reconnect_timeout_ms = 1000;
opt.connection.reader.sep = "\n";
opt.connection.writer.sep = "\n";

opt.connection.input_handler =
  [](data_ptr d, io_id_t, output_handler_t)
{
  if ( d != nullptr )
    std::cout << std::string(d->begin(), d->end()) << "\n";
};

client->start(opt);
```

`async_connect = true` уводит установление соединения с синхронного `connect` на асинхронный путь Asio. Разделитель `\n` должен совпадать с серверным — иначе стороны будут по-разному видеть границы реплик.

Чтение клавиатуры выполняется в отдельном потоке: блокирующий `getline` не должен стоять на том же потоке, где крутится `io.run()`. Отправка в сокет ставится в очередь `io_context` через `asio::post`:

```cpp
std::thread input([&]()
{
  std::string line;
  while ( std::getline(std::cin, line) )
  {
    boost::asio::post(io, [client, line]()
    {
      client->send( make(line) );
    });
  }
  boost::asio::post(io, [&]() { io.stop(); });
});
```

### Повторное подключение

После обрыва клиент может подождать и вызвать connect снова. Интервал задаётся `reconnect_timeout_ms`, но самой паузы в Asio «из коробки» в options нет: нужен колбэк `delayed_handler` — функция вида «вызови этот handler через N миллисекунд».

В прикладных демонах на базе WFC сюда обычно передают `wflow::workflow::safe_post`. В учебном примере достаточно таймера Asio, чтобы не тянуть лишнюю сущность в объяснение:

```cpp
opt.args.delayed_handler =
  [&io](std::chrono::milliseconds ms, std::function<void()> handler)
{
  auto timer = std::make_shared<boost::asio::steady_timer>(io, ms);
  timer->async_wait([timer, handler](const boost::system::error_code& ec)
  {
    if ( !ec ) handler();
  });
};
```

Если `delayed_handler` не задан, первичное соединение всё равно устанавливается, но поведение при обрыве ухудшается: либо немедленный `asio::post` без паузы (риск шторма переподключений), либо только запись в лог. Для чата с ожиданием «сервер подняли — клиент сам вернулся» таймер нужен.

## Что сознательно опущено в примере

Пример рассчитан на ясность, а не на полноту продукта:

* нет объявлений `fas::aspect` и собственных advice;
* нет своего класса Connection — используются типы из `iow::ip::tcp::*`;
* нет JSON, RPC, авторизации и отдельных «комнат» — только общая рассылка строк;
* нет многопоточного accept (`threads == 0`).

Когда понадобится собственный тип соединения или другой pipeline обработки, параметр подставляется в `server<...>` / `client<...>`. До этого момента достаточно конфигурации по умолчанию.

## Практические замечания

1. **Разделитель сообщений.** По умолчанию `sep` пустой. Для строкового протокола или JSON-RPC с `\r\n` его нужно задать явно на reader и writer.
2. **Поток выполнения `input_handler`.** Колбэк вызывается в контексте io-потока соединения. Долгие вычисления лучше уводить в очередь рабочих потоков, а в сокет отвечать через сохранённый `output_handler`.
3. **Ограничения.** У буферов чтения/записи есть `maxsize`, у acceptor’а — `max_connections`. Имеет смысл сверяться с options при переносе примера в долгоживущий сервис.
4. **Имя хоста и IP.** Если в `addr` передан числовой IP, клиент не обращается к DNS. Для символического имени выполняется асинхронный resolve, чтобы не блокировать io-поток на время опроса DNS.

## Возможные следующие шаги

На том же каркасе можно наращивать протокол, не меняя модель колбэков:

* поверх строк — сериализация (в экосистеме рядом используются wjson / wjrpc);
* несколько исходящих соединений с обходом — `multi_client` / `multi_thread`;
* параллельный accept — `opt.threads`;
* демон с конфигурацией, метриками и перезагрузкой настроек — пакет **wfc_io** (`server_tcp`, `client_tcp`) поверх iow.
